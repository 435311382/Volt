# 协议说明

<sub>[English](PROTOCOLS.md) · 简体中文</sub>

这里的内容全部来自向真实硬件发送报文并读取回包。凡是引用他人来源的地方，都注明了仓库。

两台受支持的设备都基于 **Compx** 无线电平台，但它们的帧格式并不相同。它们都不暴露标准的 HID 电量用途页（`0x06 / 0x20`），所以 Windows 永远看不到它们有电池。电量只能通过用途页为 `0xFF02` 的厂商私有集合读取。

---

## Compx / ATK 系列 —— 17 字节报文

ATK X1 SE 使用，2.4G 接收器（`373B:10C9`）和 USB 有线（`373B:1107`）走同一套。集合为 `FF02/0002`，输入输出报文长度均为 17。

### 帧结构

```
[0]     报告 ID              0x08
[1]     命令                 0x04 = 取电量
[2]     状态
[3..4]  EEPROM 地址，大端
[5]     数据长度
[6..15] 载荷
[16]    校验和
```

### 校验和

```
checksum = (0x55 - sum(bytes[0..15])) & 0xFF
```

首两字节为 `08 04`、其余全零的帧，`sum = 0x0C`，所以校验和字节为 `0x49`。这就是最短的可用请求：

```
08 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49
```

设备校验的是整帧，不只是校验和字节。把 `[2]` 字节填成 `0x3D` 让和恰好凑成 `0x49`，结果是超时 —— 设备在检查载荷字段与命令是否自洽，而不是只算对算术。

### 回包

```
08 04 00 00 00 02 32 00 0E A3 00 00 00 00 00 00 64
              ^^ ^^ ^^^^^
              |  |  └── [8..9] 电池组电压，大端，mV  (0x0EA3 = 3747 mV)
              |  └───── [7]    充电标志，1 = 充电中
              └──────── [6]    电量百分比，0..100
```

`[16]` 是回包的校验和，公式相同。**Volt 会验证它**：只有整帧 17 字节之和模 256 等于 `0x55` 才认，而不是只看头两个字节是不是 `08 04`。

这道额外的检查比看上去重要。这个接口上还跑着别的流量，一条恰好以 `08 04` 开头、但并不是电量回包的帧，`[6]` 读出来就是垃圾 —— 实测见过 116、123、127。校验和能在解析之前把这些帧挡掉。

只有电压严格落在 `2000 < mV < 5000` 之内才被接受 —— 开区间，`2000` 和 `5000` 本身会被拒绝。这样可以把那些字段一直留零的设备过滤掉。

### 接口上的坑

ATK 接收器会暴露**两个** `FF02/0002` 集合：一个 20 字节的（`col04`），一个 17 字节的（`col05`）。只有 17 字节那个接受这条帧。往 `col04` 写 20 字节返回 `ERROR_INVALID_FUNCTION` (1)；写 17 或 19 字节返回 `ERROR_INVALID_PARAMETER` (87)。

这一点很要命，因为简单的 `FirstOrDefault` 遍历匹配集合时会先挑中 20 字节那个。Volt 之所以同时按 VID/PID **和**两个报文长度匹配，就是为了这个。

## AULA 系列 —— 20 字节报文

AULA F99 使用，走 2.4G 接收器（`3554:FA09`）。集合为 `FF02/0002`，输入输出都是 20 字节。

### 请求

```
13 CA 00 00 ... 00 <sum8>
```

`sum8` 是前 19 字节求和后的低字节，这条帧算出来是 `0xDD`。

### 回包

```
13 4A 01 00 02 33 10 00 00 00 00 00 00 00 00 00 00 00 00 A3
^^^^^^^^^^^ ^^ ^^
    |        |  └── [6] 状态：0x10 = 充电中，0x01 = 放电中
    |        └───── [5] 电量百分比，0..100  (0x33 = 51)
    └────────────── [0..4] 固定前缀
```

其他 AULA 型号以及同一个 VID 上的 LEOBOG 键盘也在用同一条命令。第三方项目（[AulaTray](https://github.com/brhnshn/AulaTray)、[AulaMonitor](https://github.com/Makkksx/AulaMonitor)）在 `0xFF02` / `0x13 0x4A` 上是一致的。

同一个接口上还有**第二种回包形状**：

```
13 0A 01 00 04 05 60 10 00 00 00 00 00 00 00 00 00 00 00 97
^^^^^^^^^^^^^^^^^ ^^ ^^
       |           |  └── [7] 状态，编码同上
       |           └───── [6] 电量百分比  (0x60 = 96)
       └───────────────── [0..5] 固定前缀
```

两种回包是同一把键盘在几秒之内先后吐出来的。`13 0A` 这种是 `13 05 01` 查询的回包 —— 也就是 [2.4g-battery-tray-python](https://github.com/ahutsunboy/2.4g-battery-tray-python) 用的那条子命令，它从下标 6 读百分比。所以这个接口至少响应两种命令、回两种布局，只认 `13 4A` 的解析器会把每一条 `13 0A` 都当成没应答。Volt 同时匹配两种前缀，并按各自的前缀取对应偏移上的百分比。

### 接口上的坑

这条 HID 通道会在两次读取之间间歇性消失 —— 打开成功，下一次打开却返回 `ERROR_FILE_NOT_FOUND` (2)。每次采样前重新枚举一次就好了。Volt 的做法是：每轮扫描枚举一次，每次尝试都重新开句柄。

## 休眠行为

两台设备都不主动推送报文。都必须轮询，而且闲置后都会安静下来：

- 键盘在几分钟无输入后不再应答。按一下任意键就能唤醒。
- 鼠标在使用中应答稳定。

因为失败表现为超时而不是报错，Volt 会保留最后一次成功读数，并标注成 `上次 HH:mm`。旧值也比空行强。

注意轮询会重置设备的空闲计时器，会费一点电。Volt 在面板打开时每 5 秒轮询一次，面板收起时每 45 秒一次；这个空闲间隔刻意高于这类键盘普遍使用的 30–60 秒休眠计时器，避免轮询反而把设备一直唤醒。

## 电量怎么读

原始的电量字节比看上去要吵，而解决办法不是把它抹平。

锂电池端电压带载会被拉低，负载一撤又回升。任何靠电压估算电量的设备 —— 这些外设就是这么干的 —— 都会在你停手的那一刻、或者拔掉充电线的那一刻，报出一个**更高**的电量。键盘读到 96%、拔线掉到 84%、又爬回 96%，机理就在这里。

微软的蓝牙配件指南把这个问题定死了：电量是**只降不升**的属性。只有设备接在充电器上，或者电池被物理取下重装，才允许上升。同一份文档给出的例子正是这个场景 —— 鼠标测到 5%，进入低功耗状态，负载下降后测到 10% —— 并且明确要求上报值必须仍然是 5%。

Volt 在 `src/Filter.cs` 里实现这条规则，另外加了三道保护：

- **坏值直接丢。** `[6]` 落在 1..100 之外就不采信，也不做截断。
- **大幅下降要持续。** 单个坏帧本来会永久锁死显示，因为值现在只能降不能升。跌幅超过一个点时，只有在读数持续低于原值满 10 秒、且至少读到两次之后才采信。掉一个点以内立即采信，那是正常放电。
- **间隔太久就重新同步。** 两次读数之间隔了 5 分钟以上 —— 睡眠、休眠、程序刚启动 —— 新值直接采信。否则就是一个再也涨不回去的陈旧数字。

切换连接方式（接收器 ↔ 有线）同样触发重新同步，理由和微软允许换电池后上升一样：中间发生了什么，我们没看见。

为什么不用平均、中位数滤波或者卡尔曼滤波？因为这里的噪声不是围绕真值的测量噪声，而是随负载出现和消失的系统性偏置。把它抹平，得到的是一个滞后于现实、而且仍然会朝错误方向动的数字。只降不升这条规则直接从源头上消除了朝错误方向的移动，同时保留了真实的放电曲线。

## 发现新设备

1. 枚举 HID 集合，找带厂商用途页（`>= 0xFF00`）、且输入输出长度相等的集合。
2. 用已知的命令字节发一条帧，读回包。
3. 对比不同充电状态、不同电量下的回包，找出百分比字节和充电标志。

如果厂商提供了基于 WebHID 的配置页面，读它的 JavaScript 比抓 USB 流量更快 —— 帧结构通常就写在里面。

`docs/ADDING-A-DEVICE.zh-CN.md` 会讲怎么把结果接进设备目录。
